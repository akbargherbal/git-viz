Testing/Test Setup
Beginner 
import { render, screen } from "@testing-library/react";

What

Named imports of core React Testing Library utilities for rendering components and querying the DOM

Why

React Testing Library provides a user-centric testing approach that queries components as users would interact with them. 'render' mounts React components in a test environment, while 'screen' provides a global query interface for finding elements. This approach encourages testing behavior over implementation details and promotes accessible component design.

How

The render function creates a virtual DOM representation of the component, and screen provides query methods (getByText, getByRole, queryByText, etc.) that search this DOM. These utilities abstract away direct DOM manipulation and provide helpful error messages when elements aren't found.

Context

Used throughout the test suite to render the DebtView component and query for expected elements in the rendered output. Every test uses render() to mount the component and screen queries to verify its output.

Alternatives

Enzyme (older library with shallow/mount rendering); direct ReactDOM.render with manual DOM queries; React Test Renderer for snapshot testing; Cypress Component Testing for browser-based testing

Core Vitest testing functions for organizing and asserting test cases

Why

Vitest is a modern, fast test runner built for Vite projects with Jest-compatible API. It provides: (1) Fast execution with native ESM support; (2) Hot module replacement for tests; (3) Jest-compatible API for easy migration; (4) Built-in TypeScript support; (5) Better performance than Jest for Vite-based projects. How

describe() creates test suites (groups of related tests), it() defines individual test cases, and expect() creates assertions with matcher methods. Vitest runs these tests in parallel by default and provides detailed failure messages.

Context

Used to structure the entire test suite with one describe block containing multiple it blocks, each testing a specific aspect of the DebtView component's behavior

Alternatives

Jest (more common but slower for Vite projects); Mocha with Chai; Jasmine; Node's built-in test runner; AVA; Tape

What

Query method that finds element containing exact text match, throwing error if not found

Why

getByText is the most user-centric query - it finds elements by their visible text content, exactly as users would see them. Benefits: (1) Tests user-visible behavior; (2) Resilient to implementation changes; (3) Encourages accessible markup; (4) Throws helpful errors when element not found; (5) Synchronous - no waiting needed for static content

How

Searches the entire rendered DOM tree for elements containing the specified text. Can accept string, regex, or function matcher. Throws error with helpful message and DOM snapshot if element not found. Returns the HTMLElement for further assertions.

Context

Used extensively throughout tests to verify expected text appears in rendered output. Queries for numbers (scores), labels, categories, and other text content.

Alternatives

getByRole (more semantic); getByTestId (implementation-coupled); querySelector (too low-level); getByLabelText (for form elements); findByText (async version)

Provides clear, semantic assertion for element presence. While getByText already throws if element not found, toBeInTheDocument makes the test's intent explicit and provides better error messages. It's part of @testing-library/jest-dom which extends Jest/Vitest with DOM-specific matchers.

CONCEPT-016

TypeScript/Type Assertions
Intermediate 
...mockFile.healthScore!

What

TypeScript operator (!) that asserts a value is non-null/non-undefined, removing null/undefined from its type

Why

Tells TypeScript compiler that despite healthScore being potentially undefined in the type definition, we know it exists in this context. Necessary here because: (1) EnrichedFileData likely has healthScore as optional; (2) We know mockFile has healthScore defined; (3) Allows spreading without type error; (4) Avoids unnecessary optional chaining in test code

How

Postfix ! operator removes null and undefined from the type union. Compiler treats the value as definitely defined. Runtime behavior unchanged - if value is actually null/undefined, runtime error occurs. Should only be used when developer is certain value exists.

Context

Used when spreading mockFile.healthScore to create variations. We know healthScore exists in mockFile, so the assertion is safe. Prevents TypeScript error about spreading possibly undefined value.

Alternatives

Optional chaining with fallback: mockFile.healthScore ?? {}; type guard before spreading; making healthScore required in mock type; using Partial type; conditional spreading

Tags
