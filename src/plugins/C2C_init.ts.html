CONCEPT-001

TypeScript/Type System
Intermediate 
/// <reference types="vite/client" />

What

TypeScript triple-slash directive that includes type definitions from a specific package or file

Why

Ensures TypeScript compiler includes Vite's client-side type definitions, which provide types for import.meta.hot (HMR API), import.meta.env (environment variables), and other Vite-specific globals. Without this, TypeScript would not recognize Vite's augmented import.meta properties.

How

Triple-slash directives are special comments processed by TypeScript compiler before normal compilation. The 'types' attribute tells TypeScript to include type definitions from the specified package. Must appear at the top of the file before any code.

Context

Used here to enable type checking for import.meta.hot API used later in the file for HMR support. This is essential for Vite projects that use HMR features.

Alternatives

Include types in tsconfig.json 'types' array; use @ts-ignore to suppress errors (not recommended); avoid using Vite-specific APIs; use type assertions like '(import.meta as any).hot'

What

Variable declaration using 'const' keyword, which creates a binding that cannot be reassigned

Why

Prevents accidental reassignment of plugin instances. Signals intent that these references should remain constant. Helps catch bugs at compile time. Modern JavaScript best practice - use const by default unless reassignment is needed. Makes code more predictable and easier to reason about.

'const' creates a block-scoped binding that must be initialized at declaration and cannot be reassigned. The value itself can be mutable (object properties can change), but the reference cannot be changed to point to a different object.

Storing plugin instances that will be registered and potentially exported. These references should never change to point to different plugin instances, making const the appropriate choice. Used consistently throughout file for all variable declarations.

CONCEPT-014

Build Tools/Hot Module Replacement
Advanced 
import.meta.hot.accept(() => {
    console.log("🔄 Hot reload detected - clearing plugin registry");
    PluginRegistry.clear();

    // Re-register plugins
    const newTimelinePlugin = new TimelineHeatmapPlugin();
    const newTreemapExplorerPlugin = new TreemapExplorerPlugin();

    PluginRegistry.register(newTimelinePlugin);
    PluginRegistry.register(newTreemapExplorerPlugin);

    console.log("✅ Plugins re-registered after HMR");
  });

What

Vite HMR API method that registers a callback to execute when this module is hot-updated, enabling the module to handle its own updates without full page reload

Why

Allows plugin initialization to update during development without losing application state or requiring full page reload. Clears old plugin registrations and creates fresh instances when code changes. Critical for development experience - developers can modify plugin code and see changes immediately. Prevents stale plugin instances from accumulating in registry.

How

When Vite detects changes to this file, it calls the accept callback before applying the update. The callback clears the registry, creates new plugin instances, and re-registers them. This ensures the registry always has the latest plugin code. The callback runs in the context of the new module version.

Context

Implementing self-accepting HMR for plugin initialization module. When this file or imported plugin files change, the callback clears and re-initializes plugins. Note the 'new' prefix in variable names (newTimelinePlugin) to distinguish from outer scope variables.

Alternatives

Full page reload (no HMR); accept with dependencies 'import.meta.hot.accept(["./plugin"], callback)'; dispose callback for cleanup; invalidate() to force full reload; no HMR handling (stale state issues)

Static method call that removes all registered plugins from the registry, resetting it to empty state

Why

Essential for HMR to prevent duplicate plugin registrations. When module hot-reloads, old plugin instances would remain in registry alongside new ones without clearing. Ensures clean state before re-registration. Prevents memory leaks and stale references during development.

How

Called within HMR accept callback before creating and registering new plugin instances. Part of the HMR update sequence: detect change → clear registry → create new instances → register new instances. Critical for maintaining registry integrity during hot reloads.

Alternatives
